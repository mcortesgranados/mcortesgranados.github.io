Expanded answer

Yes, and my default answer is the least fashionable one: a modular monolith — one deployable Angular application split into enforced feature boundaries, each feature owning its routes, its state and its API access, with a deliberately small shared kernel and an import matrix that fails lint when a feature reaches into another. Micro-frontends come second, reserved for the case where independent deployment or framework heterogeneity is a genuine requirement rather than an aspiration; the mechanics are on the Q29 proof page. Across both, a shared component library and a single source of design tokens is the mechanism that keeps four applications looking like one product. Beyond those, I have used feature-sliced design to give imports a direction, an Nx-style monorepo with affected-only builds so CI stays proportional to the change, a BFF to keep the client simple, and islands with SSR only on the pages where SEO or first paint actually demands it. Every one of those choices is written up as an ADR — problem, alternatives rejected, consequences, migration path — and judged against criteria that are measured per release rather than asserted in a slide: deploy independence, build time, change failure rate, and how long a new developer takes to ship their first feature.

One deployable Angular application split into enforced feature boundaries: each feature owns its routes, state and API access, lazy-loaded domains keep the initial bundle small, and the shared kernel holds only what every feature genuinely needs. It is my default because it delivers most of the benefit of modularity without the operational cost of separate deployments.

What the architecture design buys

Rules I apply. Name the boundaries and then enforce them mechanically, because a boundary that only exists in a diagram disappears in the next sprint; keep the shared kernel small, since everything in it becomes a reason for every feature to be released together; make the design system the single source of tokens and behaviour so consistency is a dependency rather than a review comment; give each feature a public entry point and forbid deep imports, so a library can be versioned at all; and write the decision down as an ADR with the alternatives that were rejected, because the value of an architectural decision is in the reasoning, not in the outcome.
