28. RESTful APIs with .NET

Answer as submitted

“Yes — I have designed and implemented RESTful APIs in .NET/ASP.NET Core, from endpoints and contracts through security, testing and deployment.”
Technical decision: expand. The submitted line claims the capability without showing the design decisions behind it. This page is the separate, detailed version: it shows the resource model, what each method and status code promises, the collection and error conventions, and the tests that hold the implementation to the contract.

Expanded answer

Yes, on ASP.NET Core. The API is designed resource-first: URLs are nouns, the hierarchy lives in the path, and a state transition is modelled as a sub-resource that receives a POST rather than a verb grafted onto the URL. The HTTP method carries the meaning — GET, PUT, DELETE and HEAD are idempotent, POST is not, a state conflict answers 409 while a failed precondition answers 412 and a missing one 428 — so a client can retry safely without reading the documentation. Collections are never returned unbounded: cursor pagination with a hard page-size ceiling and a documented filter/sort grammar. Every failure returns one payload shape, RFC 7807 problem details with a type, a title, a status and a traceId that matches the server log. Security is explicit per endpoint (a bearer JWT validated against the issuer's JWKS, an authorisation policy, a per-caller rate limit) and identity always comes from validated claims, never from the body. Finally, the OpenAPI document is generated from the endpoints, the SPA consumes a typed client generated from that document, and contract plus integration tests through WebApplicationFactory against a containerised database fail the build when the two drift apart.

What the API design buys

Rules I apply. Design the resource model before writing an endpoint, so verbs never end up in the URL; let the method carry the guarantee, so retries are safe by construction; require versioning in the path so a breaking change cannot reach an existing client by accident; keep a single error shape and always return a traceId, so one log query correlates the client report with the server event; take the caller identity from validated claims instead of the payload; and generate the OpenAPI document from the endpoints rather than maintaining it by hand, because a hand-written contract drifts silently.
