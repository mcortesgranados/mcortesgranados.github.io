33. SOLID and object-oriented design patterns

Answer as submitted

“Yes — SOLID and classic design patterns are the foundation of my code and architectural decisions.”
Technical decision: expand. Naming the principles proves nothing, because every developer has read the same twenty-page summary. This page is the separate, detailed version: each principle is shown as a before/after refactor of one realistic class, and the pattern catalogue names where each pattern is applied and which principle it serves.

Expanded answer

Yes, and I treat SOLID as a set of forces rather than a checklist. Single Responsibility: one reason to change per class — a service that prices, computes tax, persists, notifies and logs is five reasons to change and five reviewers for one file. Open/Closed: new behaviour arrives as a new implementation registered in the container, not as another else if in an existing method, so the class that passed review last month is not re-reviewed for a segment it never heard of. Liskov Substitution: an implementation that throws NotSupportedException from an inherited member has not satisfied the contract, and the fix is a narrower interface, not a better message — which is why the contract is stated as a test every implementation runs. Interface Segregation: a read port and a write port instead of a fourteen-member IRepository<T>, so a read-only screen depends on four members and every test double stops implementing methods it will never call. Dependency Inversion: high-level policy depends on abstractions it declares, and the composition root is the only file in the solution that names a concrete type. All five are what make the pattern catalogue usable rather than decorative: strategy, specification, decorator, adapter, factory, builder, facade, mediator, observer, template method, singleton through the container, CQRS and saga each resolve a specific force, and the same vocabulary transfers directly between .NET, Java/Spring and Python.

What applying SOLID buys

Rules I apply. Give each class one reason to change and check it by naming the person who would ask for the next change; add behaviour by adding an implementation rather than a branch; state contracts as tests that every implementation runs, so substitution is verified instead of assumed; split interfaces by client rather than by entity, because the client is what depends on them; inject everything the policy does not own, so the composition root is the single place where a concrete technology is chosen; and require every pattern in the catalogue to name where it is applied, since a pattern applied for its own sake is decoration.
