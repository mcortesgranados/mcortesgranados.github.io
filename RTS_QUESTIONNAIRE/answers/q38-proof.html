38. Asynchronous and background processing

Answer as submitted

“Yes — asynchronous and scheduled processing is a recurring part of my designs on .NET, Java, Python and cloud platforms.”
Technical decision: expand. The submitted line lists the frameworks, which is the easy half. This page is the separate, detailed version: the rule that decides what leaves the request path, the three questions a cron expression never answers, the platform choice by shape of work, and the job-level reliability concerns — lease, heartbeat, quarantine, backlog age and graceful drain — that separate a job that runs from a job that can be operated.

Expanded answer

Yes, across .NET, Java/Spring, Python and cloud-native platforms, and the framework is the least interesting part of any of it. The first decision is what leaves the request path, and I apply it mechanically: anything whose duration is decided by somebody else — a mail server, a PDF render, an export over a million rows, a third-party sync, an ETL, a model — is enqueued with an id, the response returns that id immediately, and the client polls or subscribes for the outcome. A slow dependency then degrades one screen instead of exhausting the request threads. In-process, a bounded Channel<T> behind a BackgroundService is right for work that must not survive a restart: backpressure instead of unbounded growth, a configurable consumer count, and a shutdown token honoured so a rolling deploy drains and requeues rather than truncating. For anything that has to survive a restart it stops being a channel and becomes a real queue. Scheduled jobs raise three questions a cron expression does not answer: which instance runs it (a distributed lock with a fencing token), what happens if the previous run is still going (a concurrency policy: skip, queue or replace, decided per job), and what happens if the schedule fired while the service was down (an explicit misfire policy). The platform follows the shape of the work: a plain queue for independent tasks (SQS/SNS, Kafka consumer groups, Celery), a state machine for multi-step work with retries (Step Functions), a DAG for a batch pipeline with dependencies and a backfill story (Airflow), and an in-process scheduler only where a failed job is cosmetic. Finally reliability is what makes the queue trustworthy: an idempotent handler because delivery is at-least-once, a visibility timeout extended by a heartbeat so a long job is not redelivered mid-flight to a second worker, a poison message quarantined after its attempt budget instead of retried forever, and the backlog together with the age of its oldest message as a metric with an alert — because a queue that is filling up and a queue that is being worked look identical from the outside until it is too late.

What background processing buys

Rules I apply. Move anything with somebody else's timing off the request path and return an id, because a synchronous dependency is a request thread held hostage; bound every queue so pressure produces a refusal instead of an out-of-memory kill; decide per job whether losing it is acceptable, and let that answer choose between an in-process channel and a real queue; make the handler idempotent rather than wishing for exactly-once delivery; extend the lease with a heartbeat while a long job runs, so it is not handed to a second worker mid-flight; quarantine a deterministic failure after its attempt budget instead of retrying it forever into a backlog; derive batch partitions from the logical date so a re-run overwrites instead of double-counting; and alert on backlog and the age of the oldest message, because filling and draining look the same until the queue is the incident.
