43. Design documentation and its artefacts

Answer as submitted

“Yes — I create and maintain these artefacts, and I treat keeping them current as part of the work rather than as an afterthought.”
Technical decision: expand. The submitted line names the artefacts and the intention. This page is the separate, detailed version, and it takes the harder half seriously: maintained means a mechanism, not a resolution. Each artefact has one declared source of truth, is generated from it wherever a generator exists, is regenerated in the same pull request that changes the source, and is guarded by a gate that fails when the two disagree.

Expanded answer

Yes, and the design decision behind all five artefacts is the same one: put the truth in one place and derive everything else from it. ER diagrams are a view of the schema rather than a document beside it — generated from the migrations, so the picture cannot show a dropped column or miss one added on a Friday — at two levels because there are two audiences, a conceptual model the business can read and a physical one with types and keys that the team reviews the change against. Database schemas are the DDL itself under version control, with forward-only migrations applied by CI and a data dictionary generated from it; the column comment is the only place a change of meaning gets recorded, so it is part of the review rather than an ornament. API contracts are machine-readable documents with a generator on one side and a validator on the other, which is what distinguishes them from a specification in a wiki: OpenAPI generated from the implementation or written first and asserted against it, event schemas in a registry with a compatibility mode, and a breaking-change diff in CI. Component and service architecture follows the C4 levels so each diagram answers one question, with the container and component views generated from the deployment manifests and the service catalogue — because the manifests are executed by the platform and therefore cannot be wrong — and with ownership and dependencies recorded as data so a review can ask whether an edge is permitted rather than squinting at a picture. Business workflows are the exception to generation, because the value is the shared understanding: the process is modelled with the owner rather than presented to them, in a versioned model that includes the exception and escalation paths, which is where the process actually lives. And the mechanism that holds it together: a documentation pipeline in the repository, where a generated artefact is regenerated in the same pull request as its source, the docs site is built from the repository on every merge so a document cannot exist outside version control, and prose is reserved for the one thing no generator can produce — the why.

What the documentation discipline buys

Rules I apply. Declare one source of truth per artefact and derive everything else from it, because two copies of the same truth means one of them is wrong; generate every artefact a generator can produce, since a diagram drawn once is a diagram that was current once; regenerate the artefact in the same pull request as the source change, because a separate documentation ticket never competes successfully with the next feature; keep the generated file in the repository so its diff is visible in review; reserve prose for the why — alternatives rejected, constraints, consequences — and accept that everything else is regenerable; name the audience of each artefact, because a document written for everybody is read by nobody; build the docs site from the repository on every merge so a document cannot exist outside version control; and give each finding an owner, since a report addressed to nobody is a report nobody fixes.
