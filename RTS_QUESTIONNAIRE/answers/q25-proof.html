25. Angular performance optimisation

Answer as submitted

“Yes — performance tuning on large Angular applications is a documented part of my practice.”
Technical decision: expand. The submitted line states the claim without the numbers that support it. This page is the separate, detailed version: it shows what was changed, in what order, and the measured before/after for each change.

Expanded answer

Yes, and always in the same order: measure first (Angular DevTools profiler plus field LCP, INP and CLS), then fix change detection (OnPush across presentational components, signals and pure pipes instead of template function calls, detached detection for high-frequency widgets), then rendering cost (stable track in @for, virtual scrolling for long lists, @defer for heavy panels), then the bundle (route-level splitting, budgets in the build, dependency review), and finally memory (every subscription, listener, timer and cache released with the component). A change is only accepted with a number attached, measured on a throttled CPU and a slow network.

How optimisation is kept honest

Rules I apply. Never optimise without a measurement on a throttled CPU; fix the change-detection work before touching the data layer; make long lists cost a viewport instead of a dataset; ship the bundle as a budget that can fail the build; verify with field data rather than one lab run; and treat a growing heap as a defect, not as a fact of life. Every entry in the table above is reproducible from a profile.
