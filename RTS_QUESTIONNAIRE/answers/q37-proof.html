37. Versioning, authz, validation, errors, logging and observability

Answer as submitted

“Yes — these six concerns are wired once in the composition root rather than recalled at each endpoint.”
Technical decision: expand. The submitted line claims the six concerns without showing a decision behind any of them. This page is the separate, detailed version: what is decided once instead of per endpoint, what a client is allowed to learn when something fails, where each validation rule lives, and what the server must record so a failure is debuggable without being leaked.

Expanded answer

Yes, and the organising principle is that a cross-cutting concern applied per endpoint is a concern that will be forgotten at one endpoint. Versioning: the version lives in the URL because that is what a client pins and can see in its logs, the api-version header is accepted as a second route for internal callers behind a gateway, and a missing version is a 400 rather than a silent default — because AssumeDefaultVersionWhenUnspecified looks helpful and is exactly how a new client binds to v1 forever. Deprecation is announced with a Sunset header plus telemetry on who is still calling it, and the OpenAPI document is generated per version. Authentication and authorization: a JWT validated against the issuer's JWKS, cached and refreshed on a key-id change, with a named policy per endpoint and a fallback policy so that a new endpoint is protected by default — the failure mode of forgetting should be an endpoint nobody can call, not one everybody can. Identity comes from validated claims and never from the payload, and a resource belonging to another tenant answers 404 rather than 403 so existence is not disclosed. Validation is three layers with three jobs: the edge checks shape and format and returns every failure at once, the domain checks the business rules and can only be reached through its aggregate, and the database keeps the constraint that survives two concurrent requests. A rule duplicated across layers is a bug. Exception handling is one handler for the pipeline that maps known failures to the right status with a machine-readable problem type, and turns an unexpected one into a 500 carrying a trace id and nothing else — no stack trace, no SQL text, no internal path. Known failures are mapped rather than caught, and expected outcomes log at Information so a real incident is not buried in anticipatable noise. Logging and observability: structured logs inside a correlation scope opened at the first middleware and closed even on failure, the same id propagated through every call and message, OpenTelemetry traces that carry it, metrics that answer rate/errors/duration per endpoint with high-cardinality dimensions deliberately forbidden, personal data redacted at the sink rather than at each call site, and health checks that separate liveness from readiness — because a liveness probe that checks a dependency restarts healthy pods when the dependency is down, which turns a partial outage into a total one.

What wiring the concerns once buys

Rules I apply. Decide the concern once in the composition root, because a concern applied per endpoint is one that gets forgotten at one endpoint; make the default safe so that forgetting produces an endpoint nobody can call rather than one everybody can; never let the caller learn more than it can act on, and keep the diagnostic detail on the server with a trace id to connect the two; give every validation rule exactly one home and let the other layers only defend it; make the expected outcomes cheap to log and the unexpected ones expensive, so the signal is not drowned by the anticipatable; forbid high-cardinality dimensions in metrics, which is what makes a metric readable and affordable; and give every alert a dashboard, a runbook and an owner, or delete it.
