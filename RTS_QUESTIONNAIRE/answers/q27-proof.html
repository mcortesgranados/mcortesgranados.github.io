27. Architectural layers API / Application / Domain / Data Access

Answer as submitted

“Yes — that four-layer model (API/Presentation, Application/Business, Domain, Infrastructure/Data Access) is my default architecture on .NET, Spring Boot and FastAPI projects.”
Technical decision: expand. The submitted line names the layers without showing what each one owns or how a single request moves through them. This page is the separate, detailed version: it walks the four layers, traces one request across all of them, and shows the same pattern in the three stacks.

Expanded answer

Yes, on .NET, Spring Boot and FastAPI alike. API / Presentation handles transport only: routing, model binding, edge validation, authentication, RFC 7807 problem details and the wire contract, expressed as DTOs so no persistence entity ever escapes. Application / Business owns one use case per operation and declares the ports it needs — repository, unit of work, clock, event publisher — which keeps the technology choice outside the use case. Domain holds the entities, aggregates, value objects and invariants with no framework reference at all, so the rules are executable documentation. Infrastructure / Data Access implements those ports: EF Core, Spring Data JPA or SQLAlchemy, messaging, storage, outbound HTTP and the composition root. The dependency direction is always inward, each responsibility belongs to exactly one layer, and the boundaries are asserted by architecture tests rather than by convention.

What the layering buys

Rules I apply. Give every responsibility exactly one home so a change has one place to land; declare ports in the inner layer and implement them outside, so the technology is a decision made at the edge; keep the wire contract in its own DTO type so the schema never becomes the API; keep the domain free of framework references so its rules can be tested without a database or a container; and enforce the direction with architecture tests, because a boundary nobody checks is a boundary that disappears in the next sprint.
