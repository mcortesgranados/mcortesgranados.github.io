8. OAuth 2.0, OpenID Connect and authorization

Answer as submitted

“Yes — OAuth2 (PKCE, client credentials) and OIDC/JWT with Entra ID, Keycloak and Auth0.”
Technical decision: expand. The submitted line names the protocols and providers but not the rules that make an implementation safe. This page is the separate, detailed version: it shows the flow per client type, the validation the API performs and the policy that decides access.

Expanded answer

Yes. Public clients use Authorization Code with PKCE and service-to-service calls use client credentials, both against an OpenID Connect provider — Microsoft Entra ID, Keycloak or Auth0 — discovered through its /.well-known/openid-configuration and JWKS endpoints. The API validates issuer, audience, lifetime and signature keys on every request instead of decoding a token and trusting it, authorization is expressed as policies over scopes and claims, refresh tokens rotate with reuse detection, and the hardening around it covers short lifetimes, CSRF/CORS strategy, secret management and audit logging.

How the implementation stays safe

Rules I apply. The flow follows the client type — PKCE for anything public, client credentials for service calls — tokens are short-lived and refreshed by rotation, and validation is centralised once at the composition root so no endpoint re-implements it. Authorization is a policy over scopes and claims with a resource-based check where ownership matters, and secrets live in Key Vault or Secrets Manager rather than in configuration files.
