45. The service fabric: communication, gateways, identity, discovery, processing

Answer as submitted

“Yes — these are the standard building blocks of the distributed systems I design: communication, gateways, identity across hops, discovery, messaging and distributed processing, all of it observable.”
Technical decision: expand. The submitted line lists the building blocks. This page is the separate, detailed version, and it is organised around what each one is for: what belongs in a gateway and what belongs nowhere near it, which of the three identity cases a call is, why discovery is now a DNS problem, and which three numbers decide whether a consumer group is correct and fast.

Expanded answer

Yes, and the fabric is a set of decisions rather than a list of products. Service-to-service communication: typed clients over REST with a deadline and a retry policy as the default, because it is debuggable and every team has the tooling; gRPC where the edge is internal, chatty and latency-sensitive, contract-first so the schema is the interface; and asynchronous messaging wherever the caller does not need an answer now, because a synchronous chain couples the availability of two services. I keep the synchronous hops needed to serve one user request to three or fewer. API gateways own what every service would otherwise repeat — TLS, routing, token validation at the edge, per-consumer rate limits, request size limits, correlation id injection, canary splitting — and hold no business logic, because logic in a gateway cannot be unit tested, versioned or rolled back with the service that owns the rule. One detail worth naming: retries at the gateway are enabled for idempotent methods only, since retrying a POST at the edge is how a gateway creates duplicate orders. Authentication distinguishes three cases: a user request validated at the edge and re-validated by every service downstream with its own policy; a service acting on behalf of that user, propagating the identity so the audit trail names the human; and a pure machine call using client credentials or mTLS with its own narrow scopes. Credentials live in a vault, tokens are never logged, and no service reads an identity from the request body. Discovery is a DNS problem on Kubernetes: a Service resolves to healthy endpoints and unready pods leave the rotation, so a client-side registry only earns its place where the platform provides nothing — and an unhealthy dependency degrades one feature rather than failing the request. Distributed processing is three numbers and a policy: the partition count caps parallelism, the ordering key decides what "in order" means (per aggregate, never global), and the commit point decides whether a crash loses or duplicates work — so commits happen after the side effect, handlers are idempotent, a dead-letter queue carries the failure, and replay is a documented operation rather than an incident.

What the fabric buys

Rules I apply. Put a deadline on every synchronous call and keep the number of them serving one request small, because each hop multiplies the chance of being slow and the difficulty of finding out why; keep the gateway to transport, identity and traffic shaping, since anything else there is logic that cannot be tested with the service that owns it; retry at the edge only where the method is idempotent; state which identity case a call is and never read an identity from the payload; let the platform do discovery and gate traffic on readiness rather than on a ping; derive throughput from partitions and consumer groups instead of bigger workers; commit after the side effect, never before; make every handler idempotent, because a rebalance at 3 a.m. will test it; and carry one correlation id from the edge through every hop, so the request can still be followed when it is the only thing anybody has.
