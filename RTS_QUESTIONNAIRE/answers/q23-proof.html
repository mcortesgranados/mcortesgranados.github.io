23. Responsive approach and cross-viewport behaviour

Answer as submitted

“My approach separates three concerns: layout adaptation, behavioural adaptation and performance per viewport.”
Technical decision: expand. The submitted line names the three concerns but not how each is implemented or where the boundary between them sits. This page is the separate, detailed version: it shows mobile-first layering, fluid before discrete breakpoints, container queries, the behaviour that must live in code rather than CSS, and the assets and accessibility work that goes with them.

Expanded answer

The approach separates three concerns so that a change in one does not fight the other two. Layout: mobile-first CSS with a named breakpoint scale, fluid grids and space tokens, container queries for anything reusable, and progressive enhancement so the smallest viewport receives the simplest correct structure. Behaviour: what CSS cannot express — navigation pattern, table versus card rendering, virtual scrolling and chart density — is driven by one observed viewport source (BreakpointObserver or matchMedia) exposed as a signal, so every component reads the same decision. Performance: responsive images with srcset/sizes, lazy loading below the fold, and per-viewport budgets for Core Web Vitals. Accessibility is verified at every breakpoint, not only on desktop: tap targets, focus order, 200% zoom and an accessibility tree that keeps its shape.

Where the line is drawn

Rules I apply. Write the smallest layout first; prefer continuous adaptation and reserve discrete breakpoints for behaviour changes; let reusable components adapt by container rather than by window; keep structural decisions in one observable viewport signal so they can be tested; serve the right asset size instead of scaling one down; verify accessibility at every breakpoint; and attach budgets so a responsive change cannot quietly cost performance.
