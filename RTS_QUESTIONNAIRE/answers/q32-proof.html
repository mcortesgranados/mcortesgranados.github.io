32. Repository and Unit of Work

Answer as submitted

“Yes — Repository and Unit of Work are patterns I have implemented across .NET, Java and Python codebases.”
Technical decision: expand. The submitted line claims the patterns and the three stacks without showing either. This page is the separate, detailed version: it shows the repository contract, the transactional boundary, how the two patterns compose with CQRS, the specification pattern and decorators, and the cases where adding a repository would make the code worse.

Expanded answer

Yes, in all three stacks, and the mechanics differ while the intent does not. Repository: the interface is declared by the domain and named for the question being asked (GetActiveByPlanAsync), never for the mechanism; complex filtering becomes a named specification instead of a leaking IQueryable; and the implementation is the only place that names EF Core, Spring Data JPA or SQLAlchemy. Unit of Work: one transactional boundary per use case — an explicit SaveChangesAsync in EF Core, the proxied @Transactional method and its persistence context in Spring, a session wrapped in a context manager in SQLAlchemy — with the outbox row written inside that same transaction so an event can never be published for a change that rolled back. The two compose with CQRS (write side through aggregates, read side through projections), with decorators for caching and logging so cross-cutting code never enters the repository, and with domain events raised inside the transaction but dispatched only after the commit. And they stop where they stop earning their place: no generic IRepository<T> CRUD over every entity, no repository wrapping a repository, no forcing a reporting screen through the domain model, and no abstraction over an ORM that is already an abstraction.

What implementing the patterns buys

Rules I apply. Declare the repository where it is needed and name its methods for the question, not the query; put every varying predicate in a specification so the rule has one home; keep one commit per use case and stage events inside the transaction so a rollback cannot leave a published lie; make cross-cutting behaviour a decorator instead of an edit to the repository; send reporting through a projection rather than through aggregates; and refuse the generic CRUD base, because a repository that only forwards Add/Update/Delete is a layer that costs a layer and explains nothing.
