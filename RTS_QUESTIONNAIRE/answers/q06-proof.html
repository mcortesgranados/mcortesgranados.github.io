6. ORM and data-access frameworks

Answer as submitted

“Yes — EF Core (code-first, migrations, LINQ) and Dapper, plus Hibernate/JPA and SQLAlchemy.”
Technical decision: expand. The submitted line is accurate but compressed — it names the frameworks without the reasoning that decides between them. This page is the separate, detailed version: it shows the call each one is used for, the SQL it produces, and the rules that keep persistence out of the domain.

Expanded answer

Yes. EF Core is my default for domain modelling and transactional writes — code-first entities, migrations under source control, LINQ translated to set-based SQL, Include with split queries for relationships, and explicit transactions committed through a Unit of Work. Dapper takes the result-set-shaped reads: reporting queries, multi-mapping over joins and stored-procedure paths where I want exact SQL with minimal mapping overhead. Behind both sits the same repository abstraction, which is also how I bring Hibernate/JPA on Java and SQLAlchemy on Python into the same shape.

$ db.Orders.Where(o => o.CustomerId == 42).OrderByDescending(o => o.CreatedAt).Take(20).ToListAsync()

EF Core translates the expression tree to set-based SQL, so filtering and paging happen in the database instead of in memory.

SELECT TOP(20) [o].[Id], [o].[CustomerId], [o].[CreatedAt], [o].[Total]
FROM [Orders] AS [o]
WHERE [o].[CustomerId] = @__customerId_0
ORDER BY [o].[CreatedAt] DESC
-- 4 ms  ·  20 rows

How the choice is made

Rule of thumb. EF Core for the majority of the domain and every transactional write, Dapper where the query is defined by its result set rather than by an entity graph, and hand-tuned SQL only when the optimiser needs explicit guidance. Whatever the tool, the query is reviewed against its execution plan before release, and persistence stays behind an interface so it can be swapped or mocked in tests.
