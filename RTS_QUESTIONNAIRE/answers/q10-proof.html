10. NoSQL databases and years of experience

Answer as submitted

“Yes — 8+ years: MongoDB, DynamoDB, DocumentDB, Neptune and Cassandra/Keyspaces.”
Technical decision: expand. The submitted line names the engines and the duration but not the modelling discipline they require. This page is the separate, detailed version: it shows how the key schema is derived, when data is embedded, and how capacity and hot keys are handled.

Expanded answer

Yes — eight plus years, mostly with MongoDB (embedding versus referencing, compound and text indexes, aggregation pipelines, TTL indexes, replica sets) and Amazon DynamoDB (single-table design, partition and sort key strategy, GSIs/LSIs, on-demand versus provisioned capacity, streams and conditional writes). I have also worked with DocumentDB for document workloads, Neptune for graph modelling and Keyspaces / Cassandra for wide-column, high-write partitions with tunable consistency. The constant across all of them is that the data model starts from the access patterns, not from the entity list.

DecisionTypical implementationWhy it is done this way
Key schemaPK + SK composite, single tableEvery screen becomes a Query against one partition; no Scan on a read path.
Secondary indexesGSI/LSI, MongoDB compound indexEach index exists to serve a named access pattern, and its cost is counted.
Embed vs referenceembed bounded lines, reference shared dataData read together is stored together, unless the list is unbounded or shared.
Consistencyeventual by default, strong where requiredCost and latency follow the requirement, not the other way round.
Idempotencyconditional writes, outbox item, streamsA retried write cannot double-apply; events are never lost.
Capacityon-demand or auto-scaled provisionedTraffic spikes are absorbed without throttling a paying customer.
Hot partitionshigh-cardinality keys, write sharding, TTLThe partition key decides whether the table scales horizontally.

How the model is kept honest

Rules I apply. List the access patterns before writing a line of schema; make each screen a partition-scoped Query; justify every index with the query it serves; embed only bounded, co-read data; keep a conditional write or an outbox item for anything that must happen exactly once; and pick the partition key as if the table will one day be 100× larger.
