49. OpenAPI/Swagger specifications and API documentation

Answer as submitted

“Yes — OpenAPI/Swagger is my standard way of defining, documenting and validating API contracts.”
Technical decision: expand. The submitted line names the standard. This page is the separate, detailed version, and its argument is that a specification is only worth its maintenance if three things hold: one source of truth per API, tools that actually consume the document, and a pipeline that fails when the implementation drifts from it. A document that is none of those is a wiki page with a schema syntax.

Expanded answer

Yes, and I use it as the contract rather than as the documentation that follows the contract. Authoring: design-first where a consumer outside the team depends on the API, because the largest value of a specification is agreeing the shape before anything is built; code-first from the implementation where the consumers are internal and the API is still moving, with Swashbuckle or NSwag in .NET, springdoc-openapi in Java and the native schema in FastAPI. What is never acceptable is both at once — a hand-written document beside a generated one — because that is how a specification becomes a guess. Tools: Swagger UI so QA and partners explore and call the API without a hand-written collection, a mock server generated from the document so front-end work starts before the endpoint exists, typed clients generated for the SPA and for partner integrations so no DTO is maintained by hand, and schema validation in the pipeline so the document cannot quietly become invalid. Governance: the versioning and deprecation policy expressed in the document itself rather than only in a wiki, one naming and pagination convention so a consumer learns it once, security schemes and rate limits documented with the actual numbers, and a catalogue generated from the documents so nobody has to ask which service and version to call. Style is written for the person integrating rather than for the person who wrote the code: every parameter and field says what it means and what happens when it is wrong, examples are realistic rather than string, the business rules a consumer would otherwise ask about are written where they will look, and every error status is enumerated with its payload so error handling is designed instead of discovered. Enforcement is what makes all of it true: a house ruleset linted on every pull request, validation against the OpenAPI dialect, a diff against the published version so a breaking change cannot ship inside an existing major version, contract tests that fail when the implementation drifts, and publication from the pipeline so the portal can never show a version that does not exist.

The contract is authored design-first when a consumer outside the team depends on it, because the largest value of a specification is agreeing the shape before anything is built. It is generated code-first from the implementation where the consumers are internal and the API is still moving: Swashbuckle or NSwag in .NET, springdoc-openapi in Java, the native schema in FastAPI. What the specification buys

Rules I apply. Have one source of truth per API and make the pipeline refuse the alternative, because two documents that disagree are worse than one that is out of date; lint the document against a house ruleset rather than relying on a review, since a rule that depends on a reviewer is a rule that lapses on a busy week; require every operation to enumerate the failures a consumer must handle, because a happy-path document produces the defect at integration time; put a realistic example on every schema, since that is the part a consumer actually reads; express versioning and deprecation inside the document with a date and a replacement, because deprecated: true alone cannot be planned around; generate the catalogue from the documents so it can never list a version that does not exist; and diff against the published version on every change, so a breaking change needs a new major version rather than an apology.
