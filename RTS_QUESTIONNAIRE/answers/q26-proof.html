26. Multi-layered .NET applications

Answer as submitted

“Yes — layered .NET solutions with explicit separation of concerns are exactly how I structure applications.”
Technical decision: expand. The submitted line states the approach without showing the rule that makes layering useful. This page is the separate, detailed version: it shows each layer's responsibility, the direction dependencies are allowed to travel, and the tests that enforce it.

Expanded answer

Yes. A typical solution is Api (controllers/endpoints, model binding, problem details, authentication — no business rules), Application (use cases, orchestration, validation, DTOs, the ports the use case needs), Domain (entities, value objects, aggregates, invariants, domain events — zero framework references) and Infrastructure (EF Core or ADO.NET, external services, messaging, storage, composition root). Dependencies point inward: Infrastructure implements interfaces declared by Application and Domain, never the reverse. Loose coupling comes from those ports; high cohesion comes from keeping a use case and the rules it protects together; separation of concerns is what makes the domain testable without a database, and the boundaries are checked by architecture tests in the build.

LayerOwnsMust not
Apitransport, auth, validation at the edge, DTOscontain business rules or query the database directly
Applicationuse cases, orchestration, ports, transactionsreference EF Core, HTTP or any outer implementation

What the layering buys

Rules I apply. Let the domain own the rules and depend on nothing; declare ports in the inner layer and implement them outside; keep the composition root as the only place that names a concrete type; map entities to DTOs at the boundary so the database shape never becomes the API contract; and enforce all of it with architecture tests, because a boundary nobody checks is a boundary that disappears in the next sprint.
