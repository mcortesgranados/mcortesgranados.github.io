29. Micro-frontends: architecture and framework

Technical decision: expand. The question asks which architecture or framework, and the submitted line names none of them. This page is the separate, detailed version: it shows each strategy with its runtime mechanics, the shared-dependency rules that keep one framework on the page, the governance, and the threshold at which I advise against the split.

Expanded answer

Yes, with three complementary strategies. Module Federation (webpack/Vite) is the one I reach for first: a host shell resolves independently deployed remotes at runtime, with the framework, the reactivity library and the design system declared as shared singletons under strict version negotiation, so a remote can never bring a second copy of Angular onto the page and a version skew fails the pipeline rather than the user's session. Web Components / Angular Elements is the incremental-modernisation tool: a component is packaged as a framework-agnostic custom element with attributes in and custom events out and shadow DOM for style isolation, so a legacy page, a React host and an Angular host can all mount it. Route-based orchestration (single-spa style) is the composition model: each vertical is owned by one team, mounted under its own route and downloaded only when that route is active, while the shell keeps exactly what must be common — authentication and token refresh, navigation, theming, error boundaries and analytics. All three only work with governance: a versioned design system, events as the sole cross-team channel, no deep imports across remotes, one CI/CD pipeline per remote and per-remote observability with a named owner. And I say no to micro-frontends when the team count, the deployment independence or the framework heterogeneity do not justify the duplicated runtime and the coordination cost — a modular monolith with a shared component library is usually the better trade.

What the micro-frontend split buys — and costs

Rules I apply. Make the shared surface explicit and small, because every shared singleton is a reason for two teams to release together; let each vertical expose a versioned contract and forbid deep imports across remotes, so the only cross-team channel is an event or the API; keep authentication, theming and error boundaries in the shell, since four implementations of token refresh is four ways to lock users out; give every remote its own pipeline, owner and telemetry so an incident has one team to page; and degrade a failed remote to a route-level fallback so one team's bad deploy cannot take the whole product down.
