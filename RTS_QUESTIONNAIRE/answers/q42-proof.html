42. Low-Level Design (LLD)

Answer as submitted

“Yes — LLD is where I spend a large part of my design effort, because it decides whether an implementation is clean and maintainable.”
Technical decision: expand. The submitted line claims the involvement. This page is the separate, detailed version: it works one feature from the design review to the artefacts it produced, and it shows the parts of LLD that are usually skipped — the sequence diagram for each error path, the transaction boundary drawn on the diagram, the open questions with an owner, and the pseudocode for the algorithm that is hard to get right.

Expanded answer

Yes, and LLD is where the maintainability of a system is actually decided, long before architecture diagrams are drawn. Class and component design: one responsibility per class, stated in a sentence a reviewer can disagree with, dependencies pointing inward through ports the calling layer owns, names taken from the ubiquitous language rather than from the ORM, and design patterns applied where they resolve a named force — a strategy because the rule varies, a decorator because the behaviour is cross-cutting — instead of because a catalogue exists. When a responsibility needs the word “and” to describe it, that is the design pointing out which two classes it wants to become. Behavioural design: a sequence diagram for the main flow and one for each way it can fail, a lifecycle expressed as an explicit state machine with the legal transitions named, the transaction boundary drawn on the diagram rather than discovered in the code, and the concurrency and idempotency rules stated in terms of what the database enforces. The error paths are the whole point, because that is where the ambiguity lives and where the implementer would otherwise have to guess. Data design: tables with the constraints that enforce the invariants, keys chosen for stability, the indexes derived from the queries the feature will actually run, a forward-only migration that applies while the previous version is still serving traffic, and an explicit mapping that keeps the persistence model, the domain object and the wire DTO from being conflated. Contract design: every endpoint designed before it is written, including which status code each failure returns, which validation rules belong at the edge and which in the domain, and how pagination behaves on the first and last page — plus versioned event schemas and the failure mode and timeout of every external integration. Deliverables and review: a design document a reviewer can disagree with, pseudocode for the algorithms that are hard to get right, testability notes written before the tests exist, and a design review before coding — after which the design evolves where the code does, in pull requests, rather than stopping at the first commit.

What good LLD buys

Rules I apply. Write the responsibility of each class as a sentence somebody can argue with, because a responsibility nobody can dispute is a responsibility nobody has examined; draw a sequence diagram for every error path and not only for the happy one, since the main flow is the part everyone already agrees on; model any lifecycle as an explicit state machine so illegal transitions are refused in one place instead of half-checked in five; mark the transaction boundary on the diagram, because discovering it in code means discovering it after the first production incident; give every invariant that the schema can enforce to the schema, since that is the only check that survives concurrency; name the index with the query it serves, or it is a write cost with no reader; state the idempotency rule per operation rather than per system; write the pseudocode for the algorithm that is hard to get right, because the tie-break and the retry are where the defects live; and list the open questions with an owner and a date, so a decision cannot be made by whoever types first.
