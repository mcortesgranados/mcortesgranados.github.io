Q1 Angular architecture Lazy loading · guards · interceptors

How do you structure a new Angular application from scratch with at least five feature modules?

Question: “This role sets up Angular applications from scratch and works on apps with at least five modules. Walk me through your initial architecture: folder layout, routing with lazy loading, and where guards, interceptors, and shared code live. Why that structure?”
What is being probed: whether the structure is a habit or a decision. The interviewer listens for a clear dependency rule (feature isolation, no cross-feature imports), a bootstrapping sequence (routing first, then auth, then design system), and the ability to explain trade-offs instead of listing folders.
Show answer · structure, code, strong signal, follow-ups

I start from the boundaries of the domain, not from the framework. Before writing code I list the business capabilities, and each capability becomes one lazily loaded feature module. Everything that is not a capability goes into three technical buckets:

  • core/ — singleton infrastructure loaded once: authentication, HTTP interceptors, guards, error handling, configuration, and logging. No UI here, no AppModule imports into features.
  • shared/ — reusable but stateless: presentational components, custom directives and pipes, form validators, utility functions. A feature may import a shared item; shared never imports a feature.
  • features/<name>/ — one folder per capability, each with its own routing module, services, state, and components. Features never import each other directly; if two features must collaborate, the contract moves into core/ or a shared service with an explicit interface.

Routing is where the architecture becomes enforceable: the root router only declares the shell and one loadChildren per feature, so a new module cannot be added without also being isolated in its own chunk. Route guards protect at the feature boundary, and interceptors are registered once in core in a deliberate order — token attachment first, then retry/refresh, then error normalisation — because the first interceptor in the array is the outermost handler for the request and the innermost for the response.

// app-routing.module.ts — the shell declares features, never their internals
const routes: Routes = [
  { path: '', pathMatch: 'full', redirectTo: 'dashboard' },
  {
    path: 'dashboard',
    loadChildren: () => import('./features/dashboard/dashboard.module').then(m => m.DashboardModule),
    canActivate: [AuthGuard]
  },
  {
    path: 'billing',
    loadChildren: () => import('./features/billing/billing.module').then(m => m.BillingModule),
    canActivate: [AuthGuard],
    canMatch: [RoleMatchGuard],          // Angular 14+: avoids downloading a chunk the user cannot use
    data: { roles: ['billing-admin'] }
  },
  { path: '**', component: NotFoundComponent }
];

// app.module.ts — interceptor order is a design decision, not an accident
providers: [
  { provide: HTTP_INTERCEPTORS, useClass: AuthTokenInterceptor, multi: true },
  { provide: HTTP_INTERCEPTORS, useClass: RefreshTokenInterceptor, multi: true },
  { provide: HTTP_INTERCEPTORS, useClass: ErrorNormalizerInterceptor, multi: true }
]

Two more decisions I make explicitly at setup: a preloading strategy (PreloadAllModules or a custom one that preloads only the routes a user is likely to visit, so lazy loading does not cost a visible delay), and a strict TypeScript and lint baseline from day one — strict: true, noImplicitAny, template type checking — because retrofitting strictness into a five-module app is much more expensive than starting with it.

Strong signal: the candidate states a rule that a reviewer could enforce in code review (“features never import features”) and connects each folder to a runtime consequence (chunk size, singleton lifetime, guard timing) rather than only to tidiness.
Likely follow-ups: When would you skip feature modules and use standalone components? · How do you prevent a shared module from becoming a dumping ground? · What breaks if a guard returns an Observable that emits twice? · How do you share state between two lazily loaded features?
Q2 RxJS Reactive forms · memory

Build a type-ahead search that hits the API on every keystroke — and explain how you keep it clean.

Question: “A user types in a search box and results must update as they type, calling a REST endpoint. Show me how you would implement it with RxJS. Then tell me how you make sure the component does not leak subscriptions or show stale results.”
What is being probed: operator fluency and, more importantly, an understanding of cancellation and lifecycle. The stale-response problem is the real test: a candidate who debounces but does not cancel will sometimes render the answer to an older keystroke.
Show answer · pipeline, operator choice, leaks, follow-ups

The stream comes from the form control, not from a DOM event, so validation and the request share one source of truth. The pipeline is: debounce to reduce requests, drop repeats, ignore empty input, cancel the in-flight request, and recover from errors without killing the stream.

readonly results$ = this.searchControl.valueChanges.pipe(
  debounceTime(300),
  map(term => (term ?? '').trim()),
  distinctUntilChanged(),
  filter(term => term.length === 0 || term.length >= 2),
  tap(() => this.loading.set(true)),
  switchMap(term => term.length === 0
    ? of([])
    : this.searchService.search(term).pipe(
        catchError(() => of([]))            // fail the request, not the stream
      )),
  finalize(() => this.loading.set(false))
);

switchMap is the important choice: it unsubscribes from the previous inner observable, so a slow response for “ang” can never overwrite the fresh response for “angular”. If the requirement changed to “run every search, do not cancel”, the operator changes to mergeMap; if it must ignore new input while one request runs, exhaustMap. Choosing between them is the actual answer to the question.

On leaks: the template consumes results$ through the async pipe, which unsubscribes automatically; I only subscribe manually when I need a side effect, and then the subscription is tied to the component lifecycle — takeUntilDestroyed(this.destroyRef) on Angular 16+, or the Subject<void> + takeUntil pattern on Angular 13/14. I avoid nested subscribe calls entirely, because they hide both the cancellation and the error path.

For repeated reads across components I add shareReplay({ bufferSize: 1, refCount: true }) so the same request is not duplicated, and I keep the HTTP layer thin: the service returns the raw payload, the component maps to view state.

Strong signal: the candidate immediately names the stale-response risk and picks the operator by the required concurrency semantics, not by habit; and can explain refCount and why an unhandled catchError inside switchMap would terminate the outer stream.
Likely follow-ups: Difference between mergeMap, concatMap, and exhaustMap in this exact UI? · How would you add retry with backoff without retrying 4xx? · When is a BehaviorSubject the wrong state container? · How do you test this pipeline deterministically?
Q3 .NET 8 Layering · DI · EF Core

Lay out a multi-layer .NET 8 API — and justify EF Core versus Dapper.

Question: “The job requires multi-layered .NET applications with clear separation between API, business, and data access, plus dependency injection and an ORM. How do you organise the solution, how do you choose service lifetimes, and when do you reach for Dapper instead of EF Core?”
What is being probed: whether “layers” means folders or dependency direction. The lifetime question is the classic trap (a scoped DbContext captured by a singleton); the ORM question separates people who have tuned a query from people who have only used the default behaviour.
Show answer · layers, DI lifetimes, EF Core vs Dapper, follow-ups

I keep four projects and one rule: dependencies point inward. Api depends on Application; Application defines the interfaces it needs; Infrastructure implements them; Domain depends on nothing. The API project contains controllers or endpoints, filters, middleware, and the composition root — nothing else. Business rules live in Application and never see HttpContext or DbContext types.

// Application: the port. No EF Core reference leaks into business code.
public interface IInvoiceRepository
{
    Task<Invoice?> GetAsync(Guid id, CancellationToken ct);
    Task<PagedResult<InvoiceSummary>> ListAsync(InvoiceFilter filter, CancellationToken ct);
}

// Infrastructure: the adapter. EF Core for writes, Dapper for reporting reads.
internal sealed class InvoiceRepository : IInvoiceRepository
{
    private readonly BillingDbContext _db;      // scoped
    private readonly IDbConnectionFactory _sql; // scoped connection factory

    public async Task<Invoice?> GetAsync(Guid id, CancellationToken ct) =>
        await _db.Invoices
                 .AsNoTracking()
                 .Include(i => i.Lines)
                 .FirstOrDefaultAsync(i => i.Id == id, ct);
}
  • Lifetimes. DbContext and repositories are scoped — one per request, so change tracking stays coherent. Stateless services (token validation, clock, mappers) are singleton. I treat a singleton that takes a scoped dependency as a defect, and I verify with ValidateScopes and ValidateOnBuild enabled outside production so the container fails at startup instead of at 3 a.m.
  • EF Core by default for aggregates, writes, and anything that benefits from tracking, migrations, and LINQ composability. AsNoTracking on every read path, projection to DTOs with Select instead of loading entities, keyset pagination instead of Skip/Take on large tables, and ExecuteUpdateAsync for bulk changes.
  • Dapper for read models: dashboards, exports, and joins across five tables where hand-written SQL is shorter, faster, and easier to profile than the generated plan. The rule I state out loud is “EF Core for behaviour, Dapper for reporting”, so the team does not end up with two competing write paths.

Cross-cutting behaviour goes in middleware or filters, not in every action: a global exception handler that returns ProblemDetails, request validation with FluentValidation, correlation IDs, and async all the way down with CancellationToken passed from the endpoint to the query so an abandoned request stops consuming a connection.

Strong signal: the candidate talks about dependency direction and captive dependencies without prompting, and gives a concrete trigger for Dapper (reporting read model) rather than “when EF is slow”.
Likely follow-ups: How do you handle a transaction that spans two repositories? · Where does validation belong? · How do you detect an N+1 in production? · What is your migration strategy for a zero-downtime deploy?
Q4 Security OAuth 2.0 · OIDC

Secure an Angular SPA and a .NET API with OpenID Connect — end to end.

Question: “We need authentication and authorization using OAuth 2.0 / OpenID Connect. Describe the flow you would implement for a browser application calling our own API, where the tokens live, and how the API validates and enforces permissions.”
What is being probed: whether the candidate knows the difference between authenticating and authorizing, whether they would put a client secret in a SPA (a common and serious answer), and whether permissions are enforced server-side rather than by hiding buttons.
Show answer · PKCE flow, token handling, API policies, follow-ups

Authorization Code with PKCE. The SPA is a public client: no client secret, no implicit flow, no password grant. The SPA redirects to the identity provider, comes back with a code, exchanges it for an access token and an ID token, and keeps the access token in memory — not in localStorage, because any script on the page could read it. A silent renewal (iframe or refresh token with rotation, depending on the provider) keeps the session alive, and the ID token is used only to read identity claims, never to authorize an API call.

On the API side, validation is delegated to the framework and never hand-rolled:

builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.Authority = "https://login.example.com/tenant";   // discovery document drives key rotation
        o.Audience  = "billing-api";
        o.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true, ValidateAudience = true,
            ValidateLifetime = true, ValidateIssuerSigningKey = true,
            ClockSkew = TimeSpan.FromSeconds(30)
        };
        o.MapInboundClaims = false;                          // keep original claim names
    });

builder.Services.AddAuthorization(o =>
{
    o.AddPolicy("invoices:write", p => p
        .RequireAuthenticatedUser()
        .RequireClaim("scope", "invoices.write"));           // scopes from the token
});

Authorization is policy-based and lives next to the endpoint, so a new route cannot be added without a decision: [Authorize(Policy = "invoices:write")]. Roles from the token are convenient but coarse; for tenant isolation I also verify the resource's owner claim against the caller, otherwise a valid token for tenant A can read tenant B by changing an id — the most common real vulnerability in this pattern.

Remaining pieces: CORS restricted to the known front-end origins with credentials only where needed; no tokens in logs; refresh-token rotation with reuse detection; short access-token lifetimes; and, when the SPA can be served behind the same site, the BFF pattern so the browser only holds an HttpOnly cookie and the server holds the tokens.

Strong signal: PKCE and “no secret in the browser” stated unprompted, plus server-side ownership checks. A candidate who mentions hiding routes in Angular as a security control is showing a front-end-only mental model.
Likely follow-ups: Access token versus ID token — which one does the API trust? · How do you handle logout across SPA and API? · What changes if the API is called by a machine instead of a user? · How do you test that a 403 path actually returns 403?
Q5 Operations Docker · Kubernetes · AI review

p95 latency tripled after a deploy. Diagnose it — and tell me how you use AI tools without outsourcing judgement.

Question: “You are on support and get an alert: p95 latency on the main API tripled ten minutes after a deployment. Walk me through your first thirty minutes. The role also expects Docker, Kubernetes, and AI-assisted development — how do those fit into your diagnosis and your code review?”
What is being probed: operational maturity under time pressure: stabilise first, then diagnose, then prevent recurrence. The AI part tests whether tooling is used as an accelerator with a verification step, or as an authority.
Show answer · triage order, Kubernetes checks, AI review gates, follow-ups

First I protect users, then I investigate. The correlation with a deployment is strong enough that the fastest mitigation is usually to roll back or shift traffic to the previous revision, because a five-minute rollback is cheaper than a thirty-minute root cause with users affected. Only after the bleeding stops do I ask why.

  1. Scope it. Is it one endpoint, one tenant, one node pool, or everything? Compare the p95 curve against the deploy timestamp and against request volume — a latency rise that tracks traffic is saturation, one that does not is a code or dependency change.
  2. Check the platform before the code. In Kubernetes: pod restarts and readiness-probe failures, CPU throttling against the limits, memory pressure and OOM kills, HPA not scaling because the metric is wrong, and DNS or connection-pool exhaustion toward the database.
  3. Check the released diff. New query without an index, an Include that turned one query into forty, a synchronous call added to a hot path, a cache removed “temporarily”, or an interceptor retrying requests and doubling load.
  4. Use telemetry, not intuition. Distributed traces to find the span that grew — API, database, or a third-party call — and structured logs keyed by correlation id so the slow requests can be sampled individually.

Container hygiene is designed in, not debugged later: a slim multi-stage image, non-root user, pinned base tags, configuration from environment or a secret store rather than the image, and distinct liveness (is the process alive?) and readiness (can it serve?) endpoints — conflating them is what turns a slow dependency into a restart loop. And deployment-wise, rolling updates with a maxUnavailable that leaves capacity, so a bad revision never removes the good one before it is proven.

On AI-assisted development: I use it where it compresses low-judgement work — reading a stack trace, summarising a pod's logs, drafting a repository method, proposing test cases for an edge condition — and I treat its output as a draft from a fast junior colleague. Three non-negotiables: the diff is reviewed line by line before it is committed, every generated query is checked against the execution plan, and nothing merges without a test that fails when the fix is removed. The judgement about blast radius and data safety stays with the engineer; that is exactly the part the tool cannot own.

Then the part interviewers rarely hear: a short blameless postmortem — timeline, contributing factors, the one alert or check that would have caught it earlier, and an owner with a date. If a query regression caused it, the action is an index plus a performance test in CI, not “be more careful”.

Strong signal: mitigation before diagnosis, platform-level checks before code-level guesses, and a concrete follow-through (index, test, alert). On AI, the candidate names a verification gate rather than either rejecting the tools or trusting them.
Likely follow-ups: How would you prove the rollback is safe for in-flight requests? · What would you instrument first if you had no tracing? · Give me a case where AI-generated code was wrong and you caught it. · How do you keep a postmortem from becoming a blame exercise?
Q6 RxJS fundamentals Definition · Observable · operators

What is RxJS, and what problem does it actually solve?

Question: “Before we go deeper into reactive code — define RxJS for me. What is it, what are its core building blocks, and why would a team use it instead of promises and event listeners?”
What is being probed: precision of the definition and correct vocabulary. A candidate who says “it's the library Angular uses for HTTP” has used RxJS but does not own the model; the interview then usually moves to what happens on unsubscribe, or to the difference between a cold and a hot observable.
Show answer · definition, building blocks, cold vs hot, when not to use it

RxJS — Reactive Extensions for JavaScript — is a library for composing asynchronous and event-based programs by using observable sequences. Its own documentation states the intent precisely: it treats “the best of the Observer pattern, the Iterator pattern and functional programming with collections” as one model, so that any stream of values over time — an HTTP response, keystrokes, a WebSocket feed, a timer — is handled with the same vocabulary: a source, a set of transformations, and a subscription that can be cancelled.

The distinction that makes the definition useful is push versus pull. A function or an iterator is pull-based: the consumer decides when to ask, and gets one value (or iterates on demand). An Observable is push-based: it emits zero to many values over time and signals termination on one of three channels — next, error, complete. A Promise is a degenerate case of the same idea: exactly one value, not cancellable, no repeated emissions.

The building blocks an interviewer expects to hear named:

  • Observable — a lazy blueprint of a producer. Nothing runs until someone subscribes; each subscription gets its own execution of a cold source.
  • Observer — the consumer contract: next, error, complete.
  • Subscription — the handle that represents a running execution. unsubscribe() is first-class cancellation, which is the main practical reason RxJS exists in a UI.
  • Operators — pure functions that take an Observable and return a new one (map, filter, debounceTime, switchMap, catchError). They do not execute anything by themselves; they describe the pipeline.
  • Subject — an Observable that is also an Observer, used for multicasting. BehaviorSubject holds a current value (state), ReplaySubject replays history, AsyncSubject emits only the last value.
  • Scheduler — controls when emissions are delivered (time-based operators, and virtual time in tests).

Cold versus hot is the consequence of that laziness: a cold Observable creates a new producer per subscriber (two subscriptions to the same HTTP call mean two requests), while a hot Observable shares one external producer (a DOM event, a socket), so late subscribers miss earlier values unless the stream is replayed or shared.

// Pull: the consumer asks, once, and cannot cancel
const value = await fetchOne();

// Push: the producer decides when values arrive; the pipeline is declarative
const clicks$ = fromEvent(button, 'click').pipe(
  debounceTime(250),
  scan(count => count + 1, 0),
  takeUntilDestroyed()
);

const sub = clicks$.subscribe({
  next: count => render(count),
  error: err => report(err),
  complete: () => log('stream finished')
});

sub.unsubscribe();   // stops the producer — no boolean flag, no race

Concretely, it solves four problems that otherwise leak into component code as ad-hoc flags: composition of several asynchronous sources into one result, cancellation of in-flight work, time as a first-class input (debounce, throttle, retry with backoff, timeout), and error recovery inside the stream rather than around it.

And the part that shows judgement: when not to use it. A single request with no cancellation, retry or combination requirement is clearer with async/await or firstValueFrom. Simple component state is often clearer as an Angular signal. The heuristic I state is “RxJS for streams and orchestration, signals for state, promises where there is exactly one value and no cancellation”.

Strong signal: the definition names observable sequences and push vs pull, the six building blocks are correct, cancellation is given as the practical driver, and the candidate can say when RxJS is unnecessary.
Likely follow-ups: Difference between Subject and BehaviorSubject in a shared service? · What does shareReplay({ refCount: true }) change about a cold HTTP stream? · Why does an operator not run until subscription? · Where does RxJS still make sense if the app uses signals?
Q7 State management Signals · BehaviorSubject · NgRx

Choose a state management approach for a five-module Angular application.

Question: “State management is in the requirements. On a five-module Angular app, how do you decide between local component state, a service with a BehaviorSubject, Angular signals, and a full store like NgRx? Give me the decision rule, not the library names.”
What is being probed: whether the candidate has paid the maintenance cost of an over-engineered store. The expected shape is an escalation ladder with explicit triggers, plus comfort with immutability and change detection.
Show answer · escalation ladder, immutability, derived state, testing

I escalate in four levels and only move up when a stated trigger is met.

  1. Component state — anything only one screen needs. No service, no abstraction; a signal or a plain property is enough.
  2. Feature service — state shared by components inside one feature: a root- or feature-scoped service exposing a read-only signal or an asObservable(), with mutations behind methods. This covers most of a five-module app, and it is where I start.
  3. Component store / feature store — when a feature has several independent async sources, needs effects, or its state is genuinely complex (wizard flows, editors, optimistic updates). Scoped to the feature, discarded with it.
  4. NgRx or an equivalent global store — when state is cross-feature and long-lived (session, cart, permissions), several unrelated actors mutate it, or the team needs a single auditable action log with devtools time travel. That is the real trigger: many writers plus auditability, not “the app is big”.

Two rules apply at every level. First, updates are immutable — always a new reference — so OnPush and signal-based change detection stay correct; mutation in place is the most common source of “the UI doesn't update” bugs. Second, derived state is computed, never stored: totals, filtered lists and permissions are computed() or selectors, so they cannot drift out of sync with their source.

@Injectable({ providedIn: 'root' })
export class CartStore {
  private readonly _items = signal<readonly CartItem[]>([]);
  readonly items = this._items.asReadonly();
  readonly total = computed(() =>
    this._items().reduce((sum, i) => sum + i.price * i.quantity, 0));

  add(item: CartItem): void {
    this._items.update(list => [...list, item]);   // new reference, OnPush-safe
  }
  remove(id: string): void {
    this._items.update(list => list.filter(i => i.id !== id));
  }
}

I also keep server data out of the store unless it is genuinely shared: the HTTP service owns the cache (with a TTL or an invalidation call), and the component owns the view model. Duplicating server entities into a store is how teams end up reconciling two sources of truth by hand.

On the cost side: NgRx adds actions, reducers, effects, selectors and facades — worth it when the audit trail and the discipline pay for themselves, expensive when a feature needs one boolean. I say that out loud in the interview because choosing the smaller tool is a decision, not a gap.

Strong signal: an explicit trigger for the store (multiple writers + auditability), immutable updates tied to change detection, derived state as computed, and a stated boundary between server cache and client state.
Likely follow-ups: How do you prevent a shared service from becoming a global variable? · Signals versus BehaviorSubject — what actually changes for the component? · How would you test this store? · How do you handle optimistic updates and rollback?
Q8 Reactive forms Validators · reusable controls

Build a typed reactive form with cross-field rules and a reusable control.

Question: “Walk me through a complex form: cross-field validation, an asynchronous check against the API, and one field that must be reused in three places. How do you keep the validation logic out of the template and testable?”
What is being probed: fluency with reactive forms beyond FormGroup basics — validator composition, where group-level rules belong, the ControlValueAccessor contract, and whether validation is treated as a domain rule or as template markup.
Show answer · typed forms, validators, CVA, testability

I build the model first with typed forms (FormBuilder with non-nullable controls on Angular 14+), because the type of the form tells you what the template is allowed to read. Cross-field rules live on the group, not on a single control — a validator on one control cannot see its siblings, which is why teams end up with duplicated comparisons in the markup.

const rangeValidator: ValidatorFn = (group: AbstractControl): ValidationErrors | null => {
  const from = group.get('from')?.value;
  const to = group.get('to')?.value;
  return from != null && to != null && from > to ? { rangeInverted: true } : null;
};

this.form = this.fb.group({
  from: [null as Date | null, Validators.required],
  to: [null as Date | null, Validators.required],
  email: ['', [Validators.required, Validators.email], [this.uniqueEmailValidator]]
}, { validators: rangeValidator });

For the asynchronous check (an email that must not already exist), the validator returns an Observable that must complete, debounces its own input, and maps errors to null instead of throwing, so a failed request does not lock the form. I keep it out of the control's updateOn hot path by using updateOn: 'blur' for that field.

For the field reused in three places, I write a ControlValueAccessor: it is the only supported way to make a custom component behave like a form control — including validation state, disabled state, and ngModel-style binding. The contract is four methods plus the provider registration; everything else (masking, formatting, currency) stays inside the component.

@Component({
  selector: 'app-money-input',
  templateUrl: './money-input.component.html',
  providers: [{
    provide: NG_VALUE_ACCESSOR,
    useExisting: forwardRef(() => MoneyInputComponent),
    multi: true
  }]
})
export class MoneyInputComponent implements ControlValueAccessor {
  writeValue(value: number | null): void { this.text = value == null ? '' : value.toFixed(2); }
  registerOnChange(fn: (v: number | null) => void): void { this.onChange = fn; }
  registerOnTouched(fn: () => void): void { this.onTouched = fn; }
  setDisabledState(isDisabled: boolean): void { this.disabled = isDisabled; }
}

Presentation stays declarative: one error-message component that maps control.errors keys to messages, so the template contains no validation logic, and markAllAsTouched() on submit so the user sees the errors that already exist. Submission is guarded by form.valid, but the server is still the authority — client validation is a UX feature, not a security control.

Testability is the reason for all of this: validators are pure functions tested directly, the CVA is tested through its host form with TestBed, and the group rules are tested without rendering anything. Template-driven forms are fine for two-field filters; they are the wrong tool the moment rules span fields.

Strong signal: group-level validators, async validator lifecycle (must complete, debounced, errors not thrown), correct CVA contract, and validation kept out of the template.
Likely follow-ups: Why must an async validator complete? · How do you validate a FormArray of dynamic rows? · What does updateOn change, and when would you use it? · How do you surface server-side field errors on the right control?
Q9 Data SQL tuning · NoSQL modelling

A report query got slow. Tune it — and tell me when this data belongs in MongoDB instead.

Question: “You have two years with SQL Server or PostgreSQL and at least one with a NoSQL database. A reporting query that used to take 200 ms now takes four seconds. How do you approach indexes and the query itself? And when would you have modelled this in MongoDB instead?”
What is being probed: method rather than folklore. “Add an index” is not an answer; reading the plan, sargability, composite column order and write-cost trade-offs are. The NoSQL half tests whether the choice follows the access pattern.
Show answer · plan reading, index design, N+1, document modelling

I start with the plan, not with an index. The actual execution plan tells me whether the cost is a scan, a bad join order, a sort spilling to disk, or a cardinality estimate that is wrong because statistics are stale. The second question is what changed: data volume, a new filter, a parameter that hits a different plan (parameter sniffing), or a query that became an N+1 after a refactor.

Then the query itself. A predicate is only index-friendly if it is sargable: wrapping the column in a function or a cast (WHERE YEAR(CreatedAt) = 2026, WHERE CAST(Id AS varchar) = @id) forces a scan even when the index exists; rewriting it as a range restores the index. The same applies to leading wildcards and to OR across different columns.

Index design follows the shape of the query: equality columns first, then the range, then the sort, and the selected columns either in the key or in an INCLUDE to make it covering. Every index is a write cost and a maintenance cost, so I add the one the plan needs rather than one per column.

-- Query: latest paid orders of a customer, newest first
SELECT Id, Total, Currency, CreatedAt
FROM   Orders
WHERE  CustomerId = @customerId
  AND  Status     = 'Paid'
  AND  CreatedAt >= @from
ORDER  BY CreatedAt DESC;

-- Covering index: equality, equality, range, then the sort direction
CREATE INDEX IX_Orders_Customer_Status_CreatedAt
  ON Orders (CustomerId, Status, CreatedAt DESC)
  INCLUDE (Total, Currency);

For the ORM side I watch the same failure from a different angle: an Include chain that produces a cartesian explosion, lazy loading firing inside a loop, or Skip/Take on a large offset. The fixes are projection to a DTO, AsSplitQuery where it applies, and keyset pagination. And for a report that is read ten thousand times a day and written once, a pre-aggregated table or a cache is cheaper than any index.

Relational or document? I choose by access pattern. This invoice/order data is relational: several entities, invariants enforced across them, ad-hoc reporting and aggregates that change shape — a normalised model with joins is exactly right. MongoDB earns its place when the aggregate is read and written as one document, the shape varies per record (catalogues, form submissions, device payloads), and the access pattern is “fetch the whole thing by key”. Modelling is then by query: embed what is always read together, reference what is unbounded or shared, and accept deliberate duplication because there are no joins to reconcile it — the application owns consistency instead of the database.

What I do not do is treat NoSQL as a default. Multi-entity transactions, constraints, and reporting across dimensions are still where relational engines are strongest, and moving a report there means giving up the guarantee that pays for it.

Strong signal: plan first, sargability and composite column order explained with a real query, write cost acknowledged, and the NoSQL decision argued from the access pattern (aggregate shape, read-by-key) rather than from scale claims.
Likely follow-ups: How do you find an N+1 in production? · What would you do about parameter sniffing? · When is denormalising the relational schema the right call? · How do you migrate a document model when the shape changes?
Q10 Quality Testing · Azure DevOps

How do you test a full-stack feature, and what gates does the pipeline enforce?

Question: “Unit tests and peer code reviews are part of the role, and so are Git and Azure DevOps. Take a feature that spans the Angular UI and a .NET API: what do you test at each level, what runs in the pipeline, and what actually blocks a merge?”
What is being probed: whether testing is a strategy or a ritual. The strongest answers name what they deliberately do not test, use real infrastructure for integration tests, and describe gates that a person cannot bypass.
Show answer · test pyramid, integration with containers, pipeline gates, review focus

I test where the risk is, and I keep the pyramid honest. Most tests are unit tests over logic that has no framework in it: domain rules in Application (xUnit, FluentAssertions), pure validators, mappers, and RxJS pipelines with marble testing so timing and cancellation are deterministic. Angular components get TestBed tests for the behaviour a user can observe — validation messages, disabled states, emitted events — not for internal method calls.

Integration tests carry the weight that unit tests cannot: the API through WebApplicationFactory against a real database in a container (Testcontainers), so migrations, SQL, constraints and the actual EF Core mapping are exercised. That is where the defects that reach production usually live. A handful of end-to-end tests (Playwright or Cypress) cover the two or three journeys the business cannot afford to break — login, checkout, the report the client asks about — and nothing more, because E2E suites are the most expensive thing to keep green.

What I deliberately do not do: assert on private methods, mock the database into meaninglessness, or chase a coverage number. Coverage is a signal for finding untested branches, never a target — a suite at 85% that passes when the feature is broken is worse than one at 60% that fails.

# azure-pipelines.yml — the gates that block a merge
trigger:
  branches: { include: [ main ] }

stages:
  - stage: ci
    jobs:
      - job: build_and_test
        steps:
          - script: dotnet restore && dotnet build --configuration Release
          - script: dotnet test ./tests --logger trx --collect "Code Coverage"
          - script: npm ci && npm run lint
          - script: npm run test -- --watch=false --browsers=ChromeHeadless
          - script: npm run build -- --configuration production
          - task: PublishTestResults@2
            inputs: { testResultsFormat: VSTest, testResultsFiles: '**/*.trx' }

On Git and Azure DevOps: trunk-based with short-lived branches, protected main that requires a green build plus at least one review, small pull requests, and build artifacts promoted between environments instead of rebuilt. Branch policies are what make the gates real — a pipeline nobody can bypass is a gate; a pipeline that can be skipped is a suggestion.

In review I look for, in this order: correctness on the unhappy path (nulls, empty lists, timeouts, concurrency), security (authorization on the new endpoint, input validation, no secrets), data safety (migrations, transactions, destructive updates), test quality (does the new test fail if the fix is reverted?), and only then readability. Formatting and naming are automated — spending review attention there is a waste of the reviewer's scarcest resource.

Strong signal: integration tests against real infrastructure, deterministic RxJS tests, an explicit “what I don't test”, and gates enforced by branch policy rather than by discipline.
Likely follow-ups: How do you test an interceptor that retries on 401? · What do you do with a flaky test? · How do you keep integration tests fast enough to run on every PR? · Which single test would you keep if you could keep only one?
